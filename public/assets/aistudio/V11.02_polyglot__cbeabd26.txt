- **`validated-lean-toolchains`**: the installer validates the toolchain against a hardcoded list; rejects unsupported toolchains with a clear error. It resolves Lean with `elan which lean`.

### lean-beam limitations (documented)
- **`let rec` unsupported**: "Proof probes through `$/lean/runAt` and `$/lean/runWith` do **not support newly introduced local `let rec` declarations**. They return a semantic failure with the original proof state and no successor handle, including when the recursion is valid in ordinary Lean."
- **`saveUnsupportedSetup`**: "Modules with batch-only `moreLeanArgs` fail with `saveUnsupportedSetup`; move shared `-D` settings to `leanOptions`, or use `lake build` when the arguments are intentionally batch-only"[reference:25].
- **Indentation-sensitive probes**: `run-at` on blank or layout-sensitive lines may fail; the common path is a single isolated snippet.
- **Handle minting**: handles are "minted, consumed, and released only by `runAt`, `runWith`, and `releaseHandle`" and "are not a cross-family LSP concept".


### Not lean-beam (do not confuse)
- **Lean Tools MCP** (`lean_run_code`, `lean_multi_attempt`, LobeHub 2026-04-18) is a **different project** (LSP-backed, high-concurrency). Do not mix its tools into this integration.


### Constraints imposed by lean-beam
- **Toolchain compatibility**: the Beam plugin must qualify for the exact Lean toolchain fingerprint; `validated-lean-toolchains` is the authoritative matrix. lean-beam defaults to **Lean 4.36.0-rc1**; on a project using v4.35.0, either add v4.36.0-rc1 to `femev-runner` or use `--custom-toolchain` with the project's toolchain (if validated).
- **LSP ownership**: lean-beam **starts its own Lean LSP sessions** with the Beam plugin; it does not attach to the existing Kimina/Pantograph/lean4monaco sessions. This is an architectural difference from `lean-lsp-mcp` (which attaches to a running LSP).
- **Session lifetime**: the CLI owns a foreground broker + private daemon; the MCP server owns a lazy multi-workspace runtime. Either way, the broker process is a subprocess of the Polyglot backend, not a container.
- **Memory cost**: each active workspace spawns its own LSP session (~2 GB RSS). Multi-workspace parallelism is expensive; enforce a workspace cap (Section 2, Task LB3).

```typescript
export interface LeanBeamRunAtRequest {
  readonly path: string;                 // relative path inside the Lean project
  readonly version: number;              // document version (Nat)
  readonly line: number;                 // 1-indexed
  readonly character: number;            // 0-indexed
  readonly text: string;                 // tactic or command block
  readonly workspace?: string;           // broker workspace name (optional; defaults to project root)
}


export interface LeanBeamRunAtHandleRequest extends LeanBeamRunAtRequest {
  // Same fields; the tool retains a handle for follow-up via run-with / run-with-linear.
}


export interface LeanBeamRunWithRequest {
  readonly path: string;
  readonly handle: string;
  readonly text: string;
  readonly workspace?: string;
}


export interface LeanBeamRunWithLinearRequest {
  readonly path: string;
  readonly handle: string;
  readonly text: string;
  readonly workspace?: string;
}


export interface LeanBeamTodoRequest {
  readonly path: string;
  readonly version: number;
  readonly startLine: number;
  readonly startCharacter: number;
  readonly endLine: number;
  readonly endCharacter: number;
  readonly workspace?: string;
}


export interface LeanBeamProbeResult {
  readonly valid: boolean;
  readonly goalsBefore: readonly string[];
  readonly goalsAfter: readonly string[];
  readonly errors: readonly string[];
  readonly handle?: string;              // present only for lean_run_at_handle
  readonly durationMs: number;
}


export interface LeanBeamClient {
  readonly id: 'lean-beam';
  isAvailable(): Promise<boolean>;
  runAt(request: LeanBeamRunAtRequest): Promise<LeanBeamProbeResult>;
  runAtHandle(request: LeanBeamRunAtHandleRequest): Promise<LeanBeamProbeResult>;
  runWith(request: LeanBeamRunWithRequest): Promise<LeanBeamProbeResult>;
  runWithLinear(request: LeanBeamRunWithLinearRequest): Promise<LeanBeamProbeResult>;
  todo(request: LeanBeamTodoRequest): Promise<readonly unknown[]>;
  listTools(): Promise<readonly McpTool[]>;
}
```


Requirements:


· Transport: stdio to lean-beam-mcp (spawned as a subprocess by the Polyglot backend). The MCP protocol revision is 2026-07-28 (preferred) or 2025-11-25 (transition).
· Registration: add to McpClientRegistry as the third external client (after lean-lsp-mcp and paperproof-mcp). Polyglot itself is a server, not a client.
· MCP 2026-07-28 compliance: lean-beam-mcp implements server/discover and per-request metadata; Logging is deprecated, so Beam writes operational logs to stderr. The Polyglot StructuredLogger captures stderr from the subprocess.
· Handle continuation: runAtHandle() mints a handle; runWith() / runWithLinear() consume it. Handles are "minted, consumed, and released only by runAt, runWith, and releaseHandle"; they are not a cross-family LSP concept.
· Workspace: the workspace field is optional; if omitted, the broker uses the default workspace (the project root detected via --root).
· No silent fallback: if lean-beam-mcp is unavailable, isAvailable() returns false; calls throw BridgeError(LEAN_BEAM_UNAVAILABLE, ...).
· Sanitization: validateProofSearchQuery on text (max 10k chars, no control chars, balanced delimiters).
· No file mutation: none of the 5 curated tools writes the file; this is a hard invariant of lean-beam.
· destructiveHint / readOnlyHint: the MCP server advertises readOnlyHint = true for lean_run_at and lean_todo, and destructiveHint = false for the retained-handle tools. Map these hints to the Polyglot McpTool.permission field: safe for all 5 curated tools.

```markdown
# Probe a tactic


Use this skill when you want to test whether a tactic would work at a given
position, without editing the file.


## Prerequisites


- `ENABLE_LEAN_BEAM=true` in the Polyglot settings.
- A saved Lean file with a known cursor position.


## Steps


1. Call `polyglot_probe_tactic` with `{ filePath, line, character, tactic }`.
2. Inspect `goalsBefore`, `goalsAfter`, `valid`, and `errors`.
3. If `valid: true` and `goalsAfter` is empty, the tactic closes the goal.
4. If `valid: true` and `goalsAfter` is not empty, the tactic progresses but does not close.
5. If `valid: false`, read `errors` and try a different tactic.


## Failure modes


- `LEAN_BEAM_UNAVAILABLE` — lean-beam is not installed or `ENABLE_LEAN_BEAM=false`.
- `LEAN_BEAM_TOOLCHAIN_UNSUPPORTED` — the project's `lean-toolchain` is not in the Beam plugin's validated matrix.


## What this skill does NOT do


- It does not certify a proof. Only the kernel (`SEAL_KERNEL_VERIFIED_TIER5`) certifies.
- It does not modify the file. Use the normal file-edit tool to apply a tactic.
```
